# Wi-Fi HaLow (802.11ah) USB radio — working notes

Status: **EXPERIMENTAL, outside the config pipeline.** This is a design/record
document for a manual bring-up, not a Nucleus subsystem yet. Nothing here is
driven by `config.yaml`, `schema.py`, `apply`, or any systemd unit. It is **not
linked from the README or the operator manual** and will not be until it is
worked into the pipeline (see [Open items](#9-open-items)).

Proven so far: a two-node encrypted HaLow mesh between **0042** and **0052**,
peer link `ESTAB`, bidirectional ping over `10.30.1.0/24`. Everything lives
under `~natak/halow`; the only system-wide change is a handful of apt build
packages.

---

## 1. Hardware

| Property | Value |
|----------|-------|
| Device | Morse Micro MM8108 USB HaLow 802.11ah transceiver |
| USB ID | `325b:8100` (`lsusb`: "Morse Micro MM81xx Wi-Fi HaLow 802.11ah Transceiver") |
| Chip revision | MM8108 **B2** (HW version `0x00000809`; rev nibble `0x8` = B2) |
| Board type | `0x0807` — read from the chip's OTP; selects the board config file |
| Kernel driver | `morse_usb` (out-of-tree) |
| Interface | one 802.11s-capable netdev; enumerates as `wlan2`/`wlan3` (name is **not** stable across reloads) |
| TX power | ~24 dBm negotiated on channel 27 |

The driver presents the radio to Linux as a **5 GHz** device: it registers only
`NL80211_BAND_5GHZ` and maps each HaLow channel to a 5 GHz stand-in channel.
`iw`, `ip`, and the kernel log therefore always show 5 GHz numbers; only
`morse_cli` reports the true sub-GHz frequency/width. See
[§6](#6-the-5-ghz-stand-in-channels).

## 2. Software components

All from github.com/MorseMicro. Built on the node against the **running kernel**
(`6.18.50+rpt-rpi-v8`).

| Component | Repo | Tag | Notes |
|-----------|------|-----|-------|
| Kernel driver | `morse_driver` | `mm8108-2.1.0` | Built `CONFIG_MORSE_USB=y` **and** `CONFIG_MORSE_VENDOR_COMMAND=y` (see below). Produces `morse.ko` + `dot11ah.ko`. |
| Firmware + board configs | `morse-firmware` | `mm8108-2.0.0` | newest MM8108 tag. Driver loads `mm8108b2-rl.bin` + `bcf_boardtype_0807.bin`. |
| wpa_supplicant (Morse fork) | `hostap` | `mm8108-2.1.0` | Built as `wpa_supplicant_s1g`; **required** for mesh (see [§5](#5-why-the-morse-wpa_supplicant-is-required)). |
| CLI | `morse_cli` | `mm8108-2.1.0` | Optional; the only tool that shows real HaLow freq/width/power. |

### Build dependencies (apt)

```
git build-essential pkg-config python3-yaml \
libnl-3-dev libnl-genl-3-dev libnl-route-3-dev libssl-dev libusb-1.0-0-dev \
linux-headers-$(uname -r)     # only if /lib/modules/$(uname -r)/build is absent
```

`libnl-route-3-dev` is easy to miss: the fork's `driver_nl80211` links
`-lnl-route-3`, and its absence fails only at the final link step.

### Non-obvious build flags

- **Driver `CONFIG_MORSE_VENDOR_COMMAND=y`.** Without it `vendor.o` is not
  compiled, yet other objects reference `morse_vendor_*` symbols
  unconditionally, so the module fails `modpost` with "Unknown symbol".
- **Driver `CONFIG_MORSE_COUNTRY="US"`.** Makefile default is `"AU"`; wrong
  country blocks AP/mesh bring-up (see [§7](#7-problems-hit-and-fixes)).
- **wpa_supplicant `CONFIG_MESH=y`.** Not set in the fork's `defconfig`.
- **wpa_supplicant `CFLAGS += -Wno-deprecated-declarations`.** The fork's DPP
  code uses OpenSSL-3.0-deprecated `EC_KEY` calls and builds `-Werror`; without
  this the build stops in `dpp_supplicant.c`.

## 3. On-disk layout (`~natak/halow`)

```
halow/
├── morse_driver/     # git mm8108-2.1.0; morse.ko + dot11ah/dot11ah.ko built here
├── morse-firmware/   # git mm8108-2.0.0
├── hostap/           # git mm8108-2.1.0; wpa_supplicant/wpa_supplicant_s1g built here
├── morse_cli/        # git mm8108-2.1.0; morse_cli built here
├── fw/morse/         # symlinks: mm8108b2-*.bin + all bcf_*.bin  (firmware search path)
├── mesh.conf         # generated by halow-up.sh each run (chmod 600)
├── halow-setup.sh    # clone + build everything, write up/down scripts
├── halow-up.sh       # load modules, join mesh
└── halow-down.sh     # stop wpa_supplicant, unload modules
```

Nothing is installed to `/lib/modules`, `/lib/firmware`, `/usr/sbin`, `/etc`,
or systemd. Modules are `insmod`'d from the build tree; firmware is found via a
runtime path override (`/sys/module/firmware_class/parameters/path`). The system
`wpa_supplicant`/`hostapd` on `wlan0`/`wlan1` are untouched — the fork runs as a
separate `wpa_supplicant_s1g` process bound to the HaLow interface only.

## 4. Usage

```bash
bash ~/halow/halow-setup.sh     # once (and after any kernel update — rebuilds the driver)
sudo ~/halow/halow-up.sh        # bring the mesh up
sudo ~/halow/halow-down.sh      # tear it down (unloads modules)
```

`halow-up.sh` derives its settings from `/etc/nucleus/config.yaml` so both
nodes match without hand-editing:

| Setting | Source | Default / value |
|---------|--------|-----------------|
| Country | `mesh.country` | `US` |
| Mesh ID | `mesh.ssid` + `_halow` | `natak_mesh_halow` |
| SAE password | `mesh.password` | (shared mesh password) |
| IP | `10.30.1.<node.id>/24` | e.g. `10.30.1.42` |
| HaLow channel | `S1G_CHANNEL` env | `27` (915.5 MHz, 1 MHz wide) |
| Operating class | `OP_CLASS` env | `68` (US 1 MHz global op class) |
| Primary 1 MHz index | `PRIM_1M_IDX` env | `0` (only valid value for a 1 MHz channel) |

Channel/op-class/index can be overridden per-run via the env vars; they **must
match on every node** in the mesh.

## 5. Why the Morse wpa_supplicant is required

Stock `wpa_supplicant` and `iw` can put the interface into 802.11s mesh mode and
even "join" at the Linux layer, but the **radio firmware never starts the
mesh**, so no beacons are sent and peers cannot be discovered.

In this driver the firmware mesh is started by exactly one command, and only
Morse's fork sends it:

- `mesh.c` creates the interface with `mesh_id_len = 0`.
- The only path that starts the firmware mesh is `morse_cmd_set_mesh_config()`
  → `morse_cmd_cfg_mesh_bss()`, driven by the vendor command
  `MORSE_CMD_ID_SET_MESH_CONFIG` (`0xA018`) handled in `command.c`.
- `mac.c` comment at the bring-up path: *"Start mesh will be handled, when
  supplicant configures mesh id and other params."*
- The fork's `wpa_supplicant/mesh.c` sends it via
  `driver->set_mesh_config(...)` under `#ifdef CONFIG_DRIVER_NL80211_MORSE`.
  Stock wpa_supplicant has no such call.

Confirmed empirically: with `iw`/stock tools the kernel log only ever shows
`morse_cmd_cfg_mesh_bss: ... stop:1` (the driver telling the firmware to *stop*
a mesh it never started). With the fork it shows `... stop:0` — mesh started.
This is why a HaLow mesh needs a **second, separate** supplicant process
(`wpa_supplicant_s1g`) alongside the system one; it does not replace it.

## 6. The 5 GHz stand-in channels

The driver registers only `NL80211_BAND_5GHZ` and translates in the `dot11ah`
module, so userspace sees 5 GHz channels and widths, **not** real HaLow ones:

| `iw` shows | Real HaLow (US) |
|------------|-----------------|
| channel 36 / 5180 MHz | S1G ch 5, 904.5 MHz, 1 MHz |
| channel 112 / 5560 MHz | **S1G ch 27, 915.5 MHz, 1 MHz** (what we run) |
| width 20/40/80/160 MHz | 1/2/4/8 MHz |

So after a successful join, `iw dev <if> info` showing `channel 112 (5560 MHz)`
is correct and expected — that is HaLow channel 27. Use `sudo morse_cli -i <if>
channel` to read the true frequency/width from the chip.

## 7. Problems hit and fixes

Each of these blocked bring-up and is baked into the scripts:

| Symptom | Cause | Fix |
|---------|-------|-----|
| `modpost: "morse_vendor_*" undefined` | `vendor.o` not built | build with `CONFIG_MORSE_VENDOR_COMMAND=y` |
| `morse: Unknown symbol crc7_be` | `insmod` doesn't resolve deps | `modprobe crc7` before `morse.ko` (scripts `modprobe -a mac80211 cfg80211 crc7`) |
| link error `cannot find -lnl-route-3` | missing dep | install `libnl-route-3-dev` |
| build stops in `dpp_supplicant.c` (`-Werror` on OpenSSL 3 deprecations) | fork's DPP code | `CFLAGS += -Wno-deprecated-declarations` |
| `ip link set up`: "Operation not permitted" (`-EPERM`) | driver country `AU` ≠ regdomain `US` | load `morse.ko country=US` |
| `set type mp`: "Device or resource busy" | NetworkManager grabbed the new iface | `nmcli dev set <if> managed no` |
| mesh join `error=-114` (already joined) | stale kernel mesh id from a prior `iw ... set meshid` auto-rejoined on link-up | `iw dev <if> set type managed` before starting the supplicant (clears stored mesh id) |
| `S1G Primary 1MHz index 3 invalid for operating BW 1` | fork default `s1g_prim_1mhz_chan_index = 3` (valid only ≥4 MHz) | set `s1g_prim_1mhz_chan_index=0` in `mesh.conf` |
| `Invalid DTIM period (0) for Mesh` | config had no DTIM; fork requires exactly 1 | set `dtim_period=1` |
| `Min beacon gap 10 must be less than beacon interval 0` | no `beacon_int` in a mesh network block defaults to 0; MBCA gap default is 10 | set `beacon_int=100` |
| up-script re-run: `insmod ... File exists` | `lsmod \| grep -q` misreports under `set -o pipefail` (broken pipe) | test `[ -d /sys/module/<name> ]` instead |

## 8. Verifying a good bring-up

Success looks like:

```
wlan2: MESH-GROUP-STARTED ssid="natak_mesh_halow" id=0
iw:    channel 112 (5560 MHz) ... txpower 24.00 dBm
dmesg: morse_cmd_cfg_mesh_bss: beaconless:0 stop:0 mbca.config:0x01   # stop:0 = started
```

Peer + traffic check (both nodes up):

```bash
sudo iw dev <if> station dump        # peer MAC with "mesh plink: ESTAB"
ping 10.30.1.<other-id>
```

Observed 0042↔0052: `mesh plink: ESTAB`, signal −8 dBm (radios adjacent),
ping 4/4, ~13 ms avg. The `tx bitrate ... VHT-MCS` line is the 5 GHz-mapped
label, **not** the real 1 MHz HaLow rate — ignore it.

## 9. Open items

Everything below is why this is not yet a Nucleus subsystem:

- **Nothing persists.** Modules via `insmod`, firmware via the sysfs path
  override, mesh via a foregrounded-then-backgrounded supplicant — all gone on
  reboot. Re-run `halow-up.sh`.
- **No routing.** The HaLow interface is not in babeld, so only
  directly-addressed `10.30.1.x` traffic flows; no multi-hop. HWMP forwarding
  is off (`mesh_fwding=0`), same as the wlan1 mesh — L3 routing is meant to be
  Babel's.
- **No firewall rules.** UFW has no stanza for the HaLow interface; `[UFW BLOCK]
  IN=wlan2` entries are expected until rules are added.
- **Kernel coupling.** The driver is built against the running kernel; a kernel
  update breaks it until `halow-setup.sh` rebuilds. A real integration needs
  DKMS or a rebuild-on-update step.
- **Unstable interface name** (`wlan2`/`wlan3`). A real integration should bind
  a stable name (e.g. `halow0`) — note the existing `USB_DEVICES`/udev
  mechanism only handles `tty` devices today, not netdevs.
- **Firmware path override is global.** Setting
  `firmware_class/parameters/path` affects every driver's firmware lookup on the
  node; a real integration should stage files under `/lib/firmware/morse`.

### Integration sketch (not yet decided)

HaLow would be a **third USB device class**, distinct from the two existing
ones (RNode → `USB_DEVICES`/udev → `/dev/nucleus/rnode`; PTT → `PTT_DEVICES` in
`voice/daemon.py`). It produces a *network interface*, not a `/dev` node. Likely
pieces: a `halow:` schema block (enabled/channel/bandwidth), derived
IP/opclass/mesh creds, a generated supplicant conf + bring-up script + networkd
file + `nucleus-halow` unit, babeld + UFW inclusion of the HaLow interface, an
`rf.py` on/off switch, and a build/deploy story for the out-of-tree driver.
Address block proposed: `10.30.1.<id>/24` (confirm it's free).
